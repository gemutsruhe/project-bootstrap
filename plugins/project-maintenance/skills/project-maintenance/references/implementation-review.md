# Implementation review

Use this route only when the user asks to evaluate an existing implementation. The maintenance assessment does not infer missing feature requirements or generate product behavior.

1. Turn the user's explicit acceptance criteria into short, unique IDs and descriptions. Supply only reviewed workspace-relative evidence paths and check commands. Set `checkDirectory` for a nested app, and pair each `reportedChecks` command with its actual `directory`; a root pass must not certify a nested package. Do not infer a criterion merely because a matching file exists. If the criteria are missing, ask for them or label any review as exploratory rather than an acceptance verdict.
2. Call `assess_implementation` on the local workspace. Its `criteria`, `checks`, `documentationDrift`, and `reviewPrompts` are leads for inspection. `requires-behavior-review` means paths exist, not that behavior works. `reported-check-failed` flags a caller-supplied failure, not an independently reproduced result. `missing-file-evidence` means the supplied path is absent, not necessarily that no alternative implementation exists. `unmapped` means the criterion has no supplied path.
3. Separate verification in the final assessment: `declared` checks come from manifests, `not-run` means no execution evidence, and `caller-reported` statuses retain the supplied source. A reported pass is not a locally reproduced pass. If the user authorizes checks, run each safe, relevant check, capture command, working directory, status and output reference, then distinguish those actual results from declarations and third-party logs. Do not treat a package script or CI file as proof it ran.
4. Inspect the relevant code and tests for each criterion before drawing a conclusion. Check edge cases and data integrity, not only route or file names. Confirm whether project documentation still describes an earlier scaffold-only state. Report a concise matrix of criterion, evidence, observed behavior/check, and remaining gap; mark anything not proven as unverified.
5. Apply contextual prompts only where source evidence suggests the risk: database schema → pool lifecycle, migrations, transactions, and DB-backed tests; tokenized edit link → leak paths, server-side mutation authorization, session expiry and rotation; rate limiter → trusted client address and multi-instance behavior. These are review questions, not automatic findings. Cite specific code or test evidence before calling a defect.

Do not run destructive commands, change production data, modify files, or claim acceptance from file presence. An assessment request alone is read-only; implement fixes only when the user separately asks for changes.

## Full evidence policy audit

Use this route only when the user explicitly asks to inspect all policy or instruction statements. It supplements ordinary implementation criteria; it does not turn generic source files into policy documents.

1. Call `assess_implementation` with `policyAudit.entryDocuments` containing the user-designated, workspace-relative Markdown or text policy documents. For the one-command **"전수감사 시작"** flow, use `policyAudit.scope: "auto"` instead: it selects conventionally named policy and instruction documents, reports its selected paths, and does not infer generic source files as policy. The tool follows only directly referenced local policy documents, returns document collection status, and never returns raw configuration values. A blocked result, stale token, or incomplete page sequence means the audit is unverified rather than partially complete.
2. Fetch every page through `policyAudit.nextPageToken`. Confirm that item IDs are unique and the collected count equals `totalItems` before evaluating coverage. Each item includes a stable ID, source path and lines, heading context, classification, and related exception IDs.
3. Judge every `policy` and `exception` item separately as `compliant`, `partially-compliant`, `non-compliant`, `unverified`, or `not-applicable`. Read the relevant implementation, tests, and documents; cite exact paths and lines. Use `context` items only to explain scope and exceptions. A passing test proves only the behavior and input range it actually covers.
4. Keep evidence provenance separate. `checks` declared by manifests or CI are not-run until executed. `reportedChecks` stay caller-reported. Add `executedChecks` only after the user has explicitly approved the exact command and the agent has run it; its supplied source must identify the execution transcript or log. An executed result supersedes a caller-reported result only for the same command and directory, while both remain visible.
5. In the final matrix include item ID, verdict, source context, observed evidence, verification provenance, enforcement gap, impact, and minimum repair. Do not substitute an overall score for this matrix. Configuration evidence may name paths, key names, scope, and safe state classifications only; never echo configuration values, environment variables, credentials, or other sensitive content.
