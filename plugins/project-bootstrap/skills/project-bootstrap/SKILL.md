# Project Bootstrap

Use the bundled `project-bootstrap` MCP server to keep selection, validation, and planning deterministic. Its tools are read-only. Treat its output as a proposal until the user approves the exact file plan; after that approval, this Skill creates the approved local bootstrap artifacts itself.

## Platform-scoped selection (version 2)

Use this route when the user wants architecture or library decisions for a web, API, Android, Expo, Flutter, native iOS, desktop, or data/AI target, especially when a workspace has multiple apps. Keep the legacy `selectedIds` route below for existing saved selections and guide-only bootstrap work.

1. Inspect the workspace. Call `list_platform_choices` for the relevant platform and show one slot at a time, including the recommended default, alternatives, source date, version baseline, and `generation` status. A default is a suggestion: set `useDefaults: true` only after the user reviews and accepts it. Build `selection: { version: 2, targets: [{ id, platformId, path, choices, useDefaults, customChoices }] }`; every target has a unique workspace-relative path. External-service slots are unselected by default. Never describe a `conditional-review` option as generation-ready.
2. Call `validate_selection` with `selection`, the inventory, and known requirements. Explain every block and warning. Do not replace an explicit user choice with a recommendation. A custom entry needs a slot, exact name, purpose, and target; it pauses runnable generation. Ask permission before looking up official documentation or package-registry metadata, send no workspace source, and present the evidence and proposed integration for separate file and command approval. Insufficient evidence means no generated integration.
3. After the user confirms the normalized choices, call `create_plan` with `selection`, inventory, and requirements. The version-2 plan contains exact file contents, evidence, proposed commands, and checks marked `not-run`. `blocked`, `recipe-preview`, `needs-custom-research`, `needs-integration-review`, `migration-review`, conflicts, and deferred files do not authorize writes or commands. A `recipe-preview` must pass candidate-specific platform build/test gates before it becomes generation-ready; extra user approval alone does not override this release gate. In an existing project, preserve all current files and obtain a target- and path-specific migration decision before changing anything.
4. For `awaiting-scaffold`, present only the exact Flutter generator command. Run it only after separate command approval, then re-inspect and re-plan. Never write post-scaffold overlays first. On a non-macOS host, native iOS files and Xcode commands remain deferred; do not claim generation or build success. For a writable version-2 plan, request approval of exact `create` paths and contents, write only those approved non-conflicting files, then seek separate approval for each installation or verification command. Do not execute `pendingCommands` while a conflict or prerequisite remains.

The version-2 recipes create platform baselines, not product features. A file-plan approval never authorizes dependency installation, SDK tools, Git operations, online lookup, cloud changes, or command execution. Preserve `selection.version` and `catalogVersion` in `.project-bootstrap/selection.yaml`.

## Guided interview and selection (legacy `selectedIds`)

1. Call `inspect_workspace` for the target workspace before asking for details that the inventory can determine. For an existing project, preserve detected programming languages, runtimes, manifests, deployment configuration, Codex settings, and user-owned files unless the user explicitly asks to replace them. The inventory returns only a redacted summary of legacy Project Bootstrap response-locale preferences in applicable user and project Codex configs; never request, echo, copy, or rewrite raw Codex configuration. If `inventory.truncated` is true, or `agentGuideEvidence.verification.collection.complete` is false, resolve the reported traversal or metadata gaps before requesting a file plan. Cache and output directory names are retained separately; their contents are not treated as source evidence. If `inventory.accessScope.mode` is `host-boundary-not-configured`, disclose that the host did not provide `PROJECT_BOOTSTRAP_ALLOWED_ROOT`; do not claim inspection is path-restricted.
2. Collect unknown decisions as a short, progressive interview. Never present the full questionnaire at once.
   - When the host exposes a structured question control in Plan mode, use it for one decision at a time. Provide two or three mutually exclusive choices, put the recommended choice first, and state each choice's consequence concisely.
   - Treat the host's `Other`/comment response as a first-class answer. Explicitly invite a comment whenever the listed choices do not fit; do not force a listed choice.
   - When a structured control is unavailable, present the same one-decision question as a numbered Markdown list ending in `Other — describe your situation`. Wait for the answer before the next decision.
   - A choice, comment, or profile confirmation only guides planning. It is never approval to write files or run commands.
3. Before asking the user to choose between catalogue-backed candidates, make those candidate records inspectable.
   - Call `list_catalog` with the relevant kind and locale. Then call `render_catalog_explorer` with only the currently shown candidate IDs, locale, and a concise comparison title. It renders candidate cards and the packaged source Markdown in the MCP Apps UI. For a single-kind language, database, framework, tool, UI-architecture, or state-management comparison, pass `allowCustom: true` so the user can specify another choice.
   - Keep an explorer comparison focused: pass no more than 12 candidates, and pass only the rankings or candidates relevant to the current decision. The explorer is read-only and never creates or edits catalogue files.
   - Let the user use the explorer's selection and optional comment control. A submitted explorer selection is a structured user answer for the current catalogue decision, not merely a transcript message. Treat its `selection.id` as selected, retain choices from other decisions, and do not ask the same choice again. A `selection.id: custom` is not a catalogue ID: confirm its exact technology name, purpose and scope, then pass it as `customChoices` to validation and planning. Never insert `custom` into `selectedIds` or silently generate configuration for an unsupported technology. Then call `validate_selection` when the accumulated choices are valid input, or render/ask the next relevant candidates. It is never approval to write files or run commands.
   - If the host does not render MCP Apps UI, retain each candidate's `path`, summary, and ID in the written response, then use the normal structured-question or Markdown-choice fallback.
4. Ask only the next decision needed, skipping facts already supplied or found in the inventory. Use this order unless the user's answer makes another question more relevant:
   1. Question-and-answer language and existing stack. Read `inventory.responseLocaleDecision` and `inventory.programmingLanguageDecision` after inspection.
      - When `responseLocaleDecision.action` is `apply-codex-setting`, use its `locale` for the interview and catalogue display without asking again. Project settings take precedence over user settings.
      - When `responseLocaleDecision.action` is `ask-user`, first ask which language the user wants for questions and answers: Korean, English, or Other. This is a display and conversation choice, never a programming-language choice.
      - When `programmingLanguageDecision.action` is `preserve-detected`, record every detected programming language as a fixed planning constraint. Do not ask the user to choose or replace it.
      - When no programming language is detected, defer that technical choice to the selected project profile and its catalogue-backed runtime options; do not use the question-and-answer language as a runtime signal.
      - Codex itself applies general user and project settings. Preserve those settings automatically by leaving their files untouched; this Skill only consumes a legacy safe `[project_bootstrap]` response locale when one already exists. Never create that table; record new Project Bootstrap choices in `.project-bootstrap/selection.yaml`.
   2. Product or service form.
   3. Delivery target stage: mockup, MVP, or production foundation. Record it as `targetStage`; it is a profile-recommendation input, not authorization to create product functionality.
   4. Starting profile. Recommend profiles using the product form, target stage, and detected stack before the user selects or overrides one.
   5. For an MVP or production foundation, ask only the next needed operational constraint: team size, expected traffic, or operations preference. For a mockup, skip these questions unless the user's answer makes one necessary.
   6. Budget sensitivity and regulatory or security requirements.
   7. Do not ask for product features, user workflows, acceptance criteria, or implementation details. The product form and target stage are only profile-recommendation inputs; this workflow generates a base project setup rather than product functionality.
   8. Do not ask for the display locale again; it was decided as the first question-and-answer language step.
5. Call `list_catalog` and `recommend` after enough context is available. Render the ranked, explainable starting profiles in the Catalog Explorer before presenting the structured choice (or text fallback). Offer two paths after the profile is chosen: use its `template.ids` as a reviewed, common starting set, or customize the relevant language, database, framework, tool, UI-architecture, and state-management choices one decision at a time. A template is not a mandatory bundle; show its IDs and let the user keep, replace, or omit each applicable choice. For a new project, offer the matching catalogue alternatives and the `custom` choice at each genuinely open decision; for an existing project, preserve the detected stack by default. For a native Android project, decide the platform and Kotlin runtime first, then ask separately for UI architecture (MVVM or MVI) and state-management implementation (Jetpack ViewModel/StateFlow, Mavericks, Orbit, or custom). Use `profile.android-native`'s MVVM and Jetpack choices only as a reviewed common starting set; never silently select Mavericks or install a library. When an explorer selection arrives, apply that exact choice as the user override for its current decision before progressing to another question; do not rerank it away or replace it silently. Never silently select a technology.
6. Call `validate_selection` with `selectedIds` and any `customChoices`. Explain every warning or block with the referenced catalogue IDs and alternatives. For custom choices, record category (`language`, `database`, `framework`, `tool`, `architecture`, or `library`), exact name, purpose, scope, and any `replacesId`; make coexistence or replacement explicit. Map a custom `ui-architecture` candidate to `architecture` and a custom `state-management` candidate to `library`, with an Android scope when applicable. A custom choice is documentation-only until its integration is separately reviewed. If a choice is blocked, ask a replacement question; do not create an implementation plan while blocked rules remain unresolved.
7. After catalogue selections are valid and before creating the file plan, configure the planned workspace-guide bundle. Call `list_workspace_guide_policies` and read [workspace-guide-interview.md](references/workspace-guide-interview.md) at this point. When configuring `AGENTS.md`, also read [agents-authoring.md](references/agents-authoring.md). The MCP tool is the authoritative list of profile IDs, defaults, and allowed fields; do not invent values.
   - For each applicable guide, use `render_workspace_guide_configurator` as the default selection path. The editor lets the user select a profile, adjust allowed fields, provide a custom explanation, and, for `AGENTS.md`, add scoped rules. Do not render or collect every guide at once.
   - Treat `submit_workspace_guide_configuration` output as the user's answer for only its `guideKey`. Retain other decisions, use the returned normalized `guideDecisions` exactly, and continue the interview. It records no durable state and never approves file writes, commands, or hosted-repository changes. Preserve any displayed read-only `reviewedCommands` unless the user explicitly returns to the command-declaration interview to change them.
   - First ask one collaboration-host decision: no hosted PR workflow, GitHub, GitLab, or Other/existing host. Record it as `workspaceSettings.collaborationHost`. A GitHub Actions catalogue choice does not by itself authorize a GitHub PR template.
   - For a generated MVP or production runtime with GitHub selected, ask whether to include a baseline CI workflow. List and render the relevant delivery catalogue candidate before accepting `delivery.github-actions`; leaving it unselected is valid and must not be treated as approval to create CI.
   - Configure one applicable guide at a time, in this order: AGENTS.md, ARCHITECTURE.md, TEAM_GUIDE.md, PLANS.md, and CODE_REVIEW.md. Ask `.github/pull_request_template.md` only when `collaborationHost` is `github`. The configurator replaces separate profile and field questions for the active guide; use one-at-a-time structured questions only as a fallback when the MCP Apps UI is unavailable.
   - For `AGENTS.md`, the configurator collects the routing profile, document structure, coding-convention baseline, function-design rule, and comment rule together. The document structure may be automatic from reviewed catalogue selections and local path evidence, or explicitly selected as router, multi-surface, service/MCP, SDK/AI, or generated/distribution. In the no-UI fallback, ask these choices one at a time. Do not infer stylistic rules from a programming language alone: preserve detected local patterns where they exist, and let the user choose a baseline for a new project.
   - Retain the user's free-text comment, and ask its focused follow-up only when the user selects a `custom` profile or field value, or leaves a comment that changes the default. A custom AGENTS rule must name the affected scope, the invariant or convention, and the safe alternative; do not record secrets, identities, or provider-specific instructions.
   - If the user supplies project purpose or domain constraints, retain them in `agents.projectContext` and structured `agents.rules` (scope, invariant, safeAlternative). Do not infer product features. When a check is missing, collect its exact working directory, coverage, kind and effects as `agents.reviewedCommands` with `confirmed: true` only after the user confirms that declaration. Confirming a command's declaration does not authorize its execution.
   - Record answers as the MCP policy object's guideDecisions keys. Do not ask for secrets, personal data, individual names, or production credentials. Do not let an answer weaken the Skill's approval gates.
8. For a selected new runtime scaffold, establish the project boundary before planning commands. A new single-runtime project must scaffold at the empty workspace root; do not silently create `apps/<name>` or any other nested project. For a new Next.js monorepo, ask the user to choose `workspaceSettings.applicationPath` as `.` or `apps/web`; the nested path requires `repository.monorepo`. Record the choice before `create_plan`. Its supported template uses npm; if the user specifies pnpm, Yarn, or Bun for that app, the planner blocks the npm command and a matching scaffold/install plan needs separate review. If the workspace is populated without the selected scaffold, stop and ask the user to open an empty workspace or explicitly plan an existing multi-app layout. Do not install Node, a package manager, SDKs, or global tools; report missing prerequisites and present them as separately approvable commands.
   - In the legacy `selectedIds` route, native Android has no supported app generator. Its UI-architecture and state-management selections produce reviewed planning records and guides only; preserve an existing Gradle project and never substitute the generic JVM build template for an Android scaffold. Use the version-2 route for a new Android recipe. Dependency versions, Gradle edits, and SDK installation still require the corresponding plan and approval.
9. Call create_plan only after the user explicitly confirms the catalogue selection, any custom choices, workspace settings, and applicable guide decisions. Pass `customChoices`, `guideDecisions`, and `workspaceSettings`. Re-inspect the workspace first when needed so existing files are never silently replaced. Present the validation summary, common-template IDs retained or replaced, custom-choice limitations, reviewed guide decisions, `agentsGuide` evidence and template preview, configuration review, bootstrap artifact paths, `conflict` and `merge-preview` paths, generated records, runtime scaffold plan, hosted manual settings, and command list. If `agentsGuide.status` is `needs-confirmation`, ask the user to correct or confirm its missing evidence before asking for file-plan approval. Ask for approval of that exact file plan before any write.
   - When `runtimeSetup.artifactWritePhase` is `post-runtime-scaffold`, do not write artifacts or seek artifact approval yet. Present the exact scaffold command, prerequisites, expected paths, network effect, and Git effect as the only pending action. The command still needs its own explicit approval.
   - After an approved scaffold completes, re-inspect the workspace, verify its expected paths, and call create_plan again. Only this fresh plan may be approved for bootstrap artifacts; it must use the generated repository map and declared package scripts or supported runtime-manifest checks. In an `apps/web` npm monorepo, review the proposed root workspace manifest separately; `npm install` is a later command approval, never an implied scaffold step.
   - For selected CI, request a reviewed `workspaceSettings.nodeVersion` and require a root npm manifest, lockfile, and declared test/build scripts before activating it. For selected Compose, request `containerPort` and verify a root Dockerfile and `.env.example`; PostgreSQL needs an explicit service design. Present any `deferred` artifact and its reason as a pending decision, not as a file to write. A selected delivery option alone does not make a runnable artifact.

## Approval gate

Do not create, edit, delete, rename, stage, commit, push, or open a pull request until the user explicitly approves the presented file plan.

For a version-2 platform plan, use the exact `artifacts[].content` for approved `create` files. Do not reinterpret it through legacy templates or write `conflict`, `migration-review`, `deferred`, or `post-runtime-scaffold` entries. The remaining numbered steps in this section describe the legacy guide bundle unless a version-2 plan explicitly includes that file and content.

After the user approves the exact file plan, execute the approved file generation in the same turn. Do not stop at a hypothetical scaffold, a code block, or a list of proposed files. A plan whose `runtimeSetup.artifactWritePhase` is `post-runtime-scaffold` is not an artifact file plan; it must first complete the separately approved runtime command and be re-planned.

1. Recheck the final validation result. If it contains a `block`, do not write; resolve it with the user first.
2. Read [`templates/README.md`](../../templates/README.md) and the mapped template for every approved bootstrap artifact. Render the ordinary guides from normalized guide decisions. For `AGENTS.md`, replace `{{AGENTS_DOCUMENT}}` with the approved `agentsGuide.markdown` exactly; it already implements the selected locale, routing, verification policy and root size budget. Do not reconstruct it from legacy `AGENTS_REPOSITORY_MAP` or other individual placeholders. Write each approved `agentsGuide.supportingDocuments` entry using its exact planned content. For `ci-workflow`, `local-container-orchestration`, `npm-workspace-root`, `android-ui-decision`, and `custom-choice-record`, use the exact planned `content`; do not render the retired generic templates. The full evidence index preserves commands omitted from the bounded root preview. Never leave unresolved placeholders or invent unreviewed technology choices.
3. For every approved artifact whose operation is `create`, create its parent directories and write the real, non-empty file at the exact planned path. Use the workspace file-editing capability (for example, `apply_patch`); do not defer the creation to the user or merely describe the content.
4. Write the selected catalogue version, catalogue decisions, `customChoices`, workspaceSettings, and reviewed guideDecisions to `.project-bootstrap/selection.yaml`, then create the decision record, validation report, architecture overview, execution plan, and approved Codex workspace guide bundle from the reviewed results. Render `{{CUSTOM_CHOICES}}` from the reviewed plan, or state `none` when empty. The bundle is `AGENTS.md`, `ARCHITECTURE.md`, `TEAM_GUIDE.md`, `PLANS.md`, and `CODE_REVIEW.md`; update `AGENTS.md` so it tells Codex when each guide is relevant. Create the approved adapter configuration and interface-contract files as well. User-defined technologies get only the planned choice record, not a fabricated runtime or database setup.
5. Do not create any artifact marked `conflict`, `merge-preview`, or `deferred`. Before every overwrite, replacement, or merge of an existing non-identical file, stop and request a path-specific decision. Never delete files or perform an automatic migration.
6. After writing, inspect the resulting paths and report exactly which files were created, which were skipped as conflicts or deferred decisions, and which commands remain pending. Do not claim a file was generated unless it exists in the workspace.
7. After a runtime scaffold, inspect the generated manifest before proposing quality checks. List only declared scripts, explicit tool commands, or standard checks evidenced by a supported runtime manifest. Use the server's per-area evidence and supported runtime checks. Flutter, Python, Go, Maven, Gradle and .NET checks require the manifest/tool evidence described in the authoring reference; Rust, Swift, plain Dart and Terraform remain explicitly unsupported for automatic command generation. A command declaration is not evidence of successful execution or harmless effects. Never run a command that would auto-install lint configuration, dependencies, or other project files; treat missing quality tooling as an unconfigured follow-up. An `npm audit` or other registry-backed audit is a separate network command and needs explicit approval. A passed check is required before reporting it as passed, and a failed or unavailable network audit is `unverified`, never clean.

Write only the planned non-conflicting local artifacts. Record the selected catalogue version and decisions in:

- `.project-bootstrap/selection.yaml`
- `docs/project-bootstrap/decision-record.md`
- `docs/project-bootstrap/validation-report.md`
- `docs/architecture/overview.md`
- `docs/project-bootstrap/execution-plan.md`
- `AGENTS.md`
- `ARCHITECTURE.md`
- `TEAM_GUIDE.md`
- `PLANS.md`
- `CODE_REVIEW.md`

`AGENTS.md` is the project-scoped Codex instruction entry point. The architecture, team, planning, and review guides are repository conventions referenced by `AGENTS.md`; do not claim that Codex automatically discovers them independently. Never create or rewrite `.codex/config.toml`; native Codex configuration remains outside this plugin's generated state. Create `.github/pull_request_template.md` only when the approved workspace settings select GitHub and the approved guide decisions include a pull-request policy. Create container and CI files only when their matching catalogue delivery option is selected. Do not create optional `.codex/skills/`, `AGENTS.override.md`, `CODEOWNERS`, or organization-specific policy files unless the user explicitly asks for them. If a planned path already exists or requires `merge-preview`, stop and ask for a path-specific decision. Never delete files or perform automatic migrations.

## Bootstrap scope

Generate only the approved base setup: Codex workspace guides, configuration, environment contracts, architecture and interface drafts, project records, optional container, CI, and pull-request files, language-specific build or analysis configuration, and the selected runtime's standard project scaffold where the plan supports one. Do not create product-specific screens, API endpoints, business logic, database schemas, sample user flows, or feature tests. Product implementation is a separate user request after bootstrap.

For a new Flutter selection, ask for the project name only if it cannot be inferred from the workspace name, then include the planned `flutter create --no-pub --project-name <project_name> .` command and its standard output paths. For a new Expo selection, include the planned `npx create-expo-app@latest . --template default --no-agents-md --yes` command and its standard output paths. For Next.js, use only the reviewed `create_plan.scaffolds[].command` at its explicit path; do not hand-write its runtime-owned package or TypeScript configuration. These commands create runtime-owned files such as `pubspec.yaml` or Expo's `package.json`, `app.json`, and `tsconfig.json`; never hand-write competing replacements first. The file-plan approval does not authorize this command. Run a generator only after the user separately approves its exact command. A Flutter SDK dependency or an Expo dependency in the inspected manifest must establish the corresponding scaffold. A generic package.json, Android directory or Dart package alone is insufficient. If the corresponding scaffold already exists, preserve it and do not rerun its generator.

## Optional implementation assessment

When the user asks to evaluate an implemented app against requirements, read [implementation-review.md](references/implementation-review.md) and use `assess_implementation` as a read-only evidence index. This does not broaden the bootstrap workflow into product implementation or authorize commands or edits.

## Commands and upgrades

Commands are a second approval boundary. List each exact command, its working directory, purpose, network effect, and expected files before running it. If the user explicitly approves the full listed batch, run that batch; otherwise request approval per command. Never run dependency installation, generators, infrastructure initialization, Git commands, or marketplace upgrades merely because a plan has been approved.

If the Project Bootstrap MCP tools are not available in the host, report the unavailable integration and stop at a non-writing explanation. Do not launch `server/dist/index.js`, reconstruct MCP protocol traffic in a terminal, or substitute manual catalogue parsing for an unavailable tool.

Checking or upgrading the marketplace may use the network. Ask before it. Do not send workspace source or bootstrap records to external services.
